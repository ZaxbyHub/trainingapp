# ADR-0003: desktop backend architecture — Node main-process server vs Electron-hosted Python sidecar

- **Status:** accepted (2026-09-21)
- **Issue:** [#57 — A7 spike: prove the packaged native stack and choose Node backend vs Electron-hosted Python sidecar](https://github.com/ZaxbyHub/trainingapp/issues/57)
- **Evidence:** `eval/adr0003-matrix.json` (machine-written comparison matrix, provenance-stamped), `eval/adr0003-e2e-evidence.json` (installed-app end-to-end records, installer sha256s, CI run URLs), `spike/measure/measure.mjs` + raw per-run JSON under `spike/measure/results/`, frozen pinning tests `tests/test_adr_0003_desktop_backend.py`; CI build evidence in `.github/workflows/spike-build.yml` runs linked from the evidence JSON. Note: the eval JSONs' `provenance.git_commit` (952ae14) is the spike/measurement commit; the JSONs themselves were committed afterwards in e8fecbb once measurement completed.

## Context

The v1 plan assumed a "Node backend, no compatibility constraint" without packaging proof; the independent review that produced this roadmap slot rejected that premise and demanded a measured comparison before WS-B commits to a shape. By the time this spike executed, WS-B had already landed on the provisional Node default: #59 (Electron scaffold), #61 (backend host with BOTH a Node mode and a sidecar mode — `desktop/main/backend/sidecar-manager.ts` explicitly anticipates "ADR-0003's Python-sidecar option"), #62 (native LLM inference), #63 (store schema), #65/#66/#67. This ADR supplies the missing decision record and tests the assumption against a packaged, installed, measured comparison.

Both slices load the A6-selected models (Quality `gemma-4-e2b-it` Q4_K_M, Fast `lfm2.5-vl-450m` Q4_K_M — ADR-0002) and the A5 embedding model (`bge-small-en-v1.5`, 384 dims) and answer the single frozen `POST /ask/stream` endpoint (contract v2.6.0, #51): SSE with CRLF separation, `{"token"}` frames, exactly one terminal event, `cancelled: true` on client disconnect, required `grounding`.

## Options considered

1. **Node main-process server** — in-process loopback HTTP server inside the Electron main process; `node-llama-cpp` for GGUF inference; `@huggingface/transformers` (onnxruntime-node) for embeddings; `better-sqlite3` + `sqlite-vec` for the store. Packaged as `spike/node-backend/` (NSIS, per-user).
2. **Electron-hosted Python sidecar** — the existing post-#51 FastAPI pipeline (`api_server.py`, `llama-cpp-python`, `sentence-transformers`, ChromaDB) frozen with PyInstaller (onedir) and spawned as a loopback child process by a minimal Electron shell that proxies the SSE stream byte-for-byte. Packaged as `spike/python-sidecar/` (NSIS, per-user) with a separate PyInstaller probe build for the reranker packaging-risk question.

## Comparison (measured, machine-tagged `devstation`)

Methodology: both slices installed from their NSIS installers on the same dev station with the same pre-staged model directory; cold start = spawn→`/health` 200 (median of 3); generation metrics from a ~2k-token prompt (8,272 chars, est. 2,068 tokens) against the warm app; peak RSS = Windows `Working Set - Peak` aggregated over the full process tree across the ready→terminal window; cancellation = client disconnect mid-generation → server-side stop confirmation with a CPU-plateau check; install size = installed directory size (models staged OUTSIDE the installer for both slices — #84 owns model packaging, so bundling them would add the same 6+ GB to both and say nothing about the backend decision). All values are written by `spike/measure/measure.mjs` into `eval/adr0003-matrix.json` and quoted here verbatim.

| Metric | Node backend | Python sidecar |
|---|---|---|
| Install size (MB, app+deps; models external) | 1373.7 MB | 1908.8 MB |
| Cold start to first-ready (s, median of 3) | 0.766 s | 4.755 s |
| First-token latency (s, 2k-token prompt) | 1.287 s | blocked: frozen llama-cpp-python access-violates in llama_model_load (PyInstaller onedir); retrieval and health serve normally |
| Decode tok/s (2k-token prompt) | 0.93 | blocked: frozen llama-cpp-python access-violates in llama_model_load (PyInstaller onedir); retrieval and health serve normally |
| Peak RSS during generation (MB, process tree) | 2124.6 MB | 327.9 MB (no LLM resident — generation blocked; embedding+retrieval only) |
| CI build reliability (clean windows runner) | 1/1 runs green (run 35641461760) | build green 1/1; artifact upload 403 flake passed on retry (run 35641461760) |
| Cancellation stop (client disconnect → server stop) | 111 ms (CPU idle confirmed within 5 s) | blocked: no generation to cancel (LLM unavailable in the frozen build) |

The python-sidecar first-token/decode/cancellation rows are BLOCKED, not omitted: the packaged sidecar boots (uvicorn + ChromaDB + bge embedding + retrieval all serve `/health` with `engine_ready: true`), but its GGUF inference crashes.

## Decision

We chose the node backend: the Electron main-process Node server (option 1) is the desktop backend architecture, confirmed as the production default for #61/#62 and the WS-B baseline going forward. `desktop/main/backend/backend/index.ts` keeps `mode: 'node'` as the default with the sidecar path remaining available for future need, now backed by measured evidence instead of an unproven assumption.

Why (from the matrix, all values above quoted from `eval/adr0003-matrix.json`):

1. The Node slice is fully proven packaged: it installs, boots in 0.766 s (median of 3), streams a real answer through the frozen contract (first token 1.287 s on the 2k prompt, 2,124.6 MB peak RSS), cancels in 111 ms with CPU work confirmed stopped, and builds green in a clean CI runner.
2. The Python sidecar is decisively blocked on packaged GGUF inference: llama-cpp-python 0.3.35 access-violates inside `llama_model_load` in ANY PyInstaller-frozen process on this toolchain, reproduced in a minimal probe and unaffected by every documented mitigation (32 MB PE stack reserve, OpenMP preloads and `KMP_DUPLICATE_LIB_OK`, real-file package layout outside the PYZ, explicit DLL search paths). The identical venv layout works, isolating the failure to the frozen environment. A desktop backend whose packaged LLM cannot load is not shippable, regardless of the remaining metrics.
3. Supporting deltas favor Node: a 535.1 MB smaller installed footprint (1373.7 vs 1908.8 MB) and a 6.2× faster cold start (0.766 vs 4.755 s), both measured before any LLM load in either slice.
4. The Python pipeline's genuine advantage — its richer, already-tested RAG pipeline — is preserved by the decision: the Node host already implements the same frozen contract and store schema (#61, #63, #65), and sidecar-manager remains in tree should a future packaged-Python capability (e.g. a PyInstaller fix upstream or a non-llama Python service) justify revisiting.

### Packaging findings the decision rests on (all machine-recorded in `eval/` + `spike/measure/results/`)

- **F1 — frozen llama-cpp-python (BLOCKER for option 2):** access violation reading `0x0` inside `llama_model_load` in the PyInstaller onedir; byte-identical `llama.dll`/`ggml*.dll` and the same GGUF succeed in the venv; reproduced in a minimal single-entry frozen probe with the load moved before any other import; unaffected by PE stack reserve 32 MB, `KMP_DUPLICATE_LIB_OK=TRUE`, torch-OpenMP preloads, and real-file (non-PYZ) package layout. Fix direction for a future revisit: an upstream llama-cpp-python release that freezes cleanly, or Microsoft's documented PyInstaller loader changes — neither exists today on the pinned stack.
- **F2 — modern scientific-Wheel generation fails frozen:** torch 2.14+cpu fails DLL init (WinError 1114, `c10.dll`), onnxruntime 1.30 segfaults at import under PyInstaller onedir; the working sidecar pin set is torch==2.2.2 / onnxruntime==1.17.3 / numpy<2 plus chromadb walk-based module collection (`collect_submodules` misses chromadb's executor/segment plugin trees), `collect_data_files('chromadb')` for importlib.resources migrations, and explicit `chromadb.migrations`/`chromadb.telemetry.product.posthog` hiddenimports.
- **F3 — the reranker packaging risk (the issue's named defect) is confirmed and is TWO defects:** (a) with the repo-pinned sentence-transformers (<3.0.0; 2.7.0 in the sidecar venv), `reranking.py:62`'s `CrossEncoder(..., local_files_only=True)` raises TypeError — the packaged 2.7 CrossEncoder does not accept the kwarg at all, so the packaged reranker cannot even construct; (b) the cache-only lookup mechanism itself reproduces: with the kwarg path exercised on a sentence-transformers that accepts it, an isolated empty HF cache yields the deterministic `OSError: We couldn't connect to 'https://huggingface.co' ... couldn't find them in the cached files`. The staged-model leg proves the packaged build CAN carry the reranker when the model files ship beside it (loaded by local path, offline). Both legs are recorded verbatim in `eval/adr0003-e2e-evidence.json` (`reranker_probe`) and `spike/measure/results/probe.txt`. Fix direction: pin/upgrade sentence-transformers consistently, stage the reranker model files into the bundle, and load by local path (or invoke `scripts/precache_models.py` at install time) — recorded as a follow-up, not fixed here (out of spike scope).

## Consequences

- The default backend mode is Node, now evidence-backed; `desktop/` production trees were not touched by the spike (the slices are standalone by construction).
- **reference-i5 rows are PENDING**: all measurements are machine-tagged `devstation` (AMD Ryzen 9 5950X / 128 GB / Windows 11 build 26200 / Arc Pro B50). Per the A2 machine-tagging rules and ADR-0002's precedent, no dev-station number is presented as a reference-laptop figure; the operator runbook is `bench/RESULTS.md` ("Reproducing on the reference laptop") extended by `spike/measure/measure.mjs`. A materially different reference-i5 result reopens this decision.
- **The spike slices are throwaway**: `spike/` and `.github/workflows/spike-build.yml` are deleted in a fast-follow commit immediately after this ADR merges. Promotion map: the measurement harness patterns (installed-exe driving, `Working Set - Peak` aggregation, server-metrics-line parsing) are the reusable part and are preserved verbatim in this ADR's git history and the evidence JSONs; the sidecar lifecycle logic already lives in `desktop/main/backend/sidecar-manager.ts` (production); nothing in `spike/` is referenced by any permanent artifact (enforced by the frozen checks, which validate only `docs/adr/` + `eval/` + `tests/`).
- The CI-build-reliability evidence (run URLs in the evidence JSON) covers the windows-latest runner; the node job built green first try; the python job's build succeeded with one transient artifact-upload 403 that passed on retry.
- **Frozen-check limitations (disclosed):** the pinning suite's C3 polarity filter matches `rerank|pyinstaller` sentences, so its guarantee is "no PyInstaller/reranker `reproduced` sentence disagrees with the JSON verdict" rather than "the reranker sentence alone matches"; the defect-identification clause still pins `reranking.py:62`/`local_files_only` scope. The matrix field `reranker_local_files_only_reproduced: true` records leg B (the cache-only offline-lookup mechanism, `HF_HUB_OFFLINE=1` + empty cache → OSError); leg A — the exact `reranking.py:62` call shape with the kwarg — cannot execute under the packaged sentence-transformers 2.7 (TypeError, recorded as `INCOMPATIBLE_KWARG` in the same JSON), which is why the ADR prose splits the two defects.
